# Обращения Platerra: подготовленный relay

Движок скопирован из `l4desk-landing/contact`, бренд и темы адаптированы.
Контракт: браузер → same-origin `/api/contact` → приватный relay → существующий
email gateway → владелец и фиксированное подтверждение посетителю.

Форма: имя, email, тема, сообщение, согласие и SmartCaptcha. Тема выбирается
по query-параметру продуктового CTA. Телефон не запрашивается и не публикуется.
Уведомление с текстом посетителя направляется только на `info@platerra.ru`;
пользователь не может подменить владельца. Посетителю отправляется фиксированное
подтверждение без пересылки его текста. Лимиты и защита повторной отправки сохранены.

## Блокер подключения

Для использования действующего шлюза авторизация `yc` не требуется.
Она нужна только при изменении самой облачной функции.
Владелец добавил домен в существующую SmartCaptcha. Повторная проверка
на origin `https://platerra.ru` успешна: виджет показывает слайдер
«Потяните вправо» без прежней ошибки домена. CAPTCHA-блокер устранён;
серверный приём реального CAPTCHA-токена ещё не проверялся.
Нельзя отключать защиту или выдавать mock CAPTCHA за рабочую проверку.

Текущий gateway API принимает recipients/subject/message и выбирает отправителя
в облачной функции. Указание `CONTACT_OWNER_EMAIL` меняет получателя, а не From.
Шлюз принял реальное проверочное уведомление на `info@platerra.ru`
через канал `platerra-landing`: status=sent и postbox_message_id присутствуют.
Владелец подтвердил фактический From тестового письма: **noreply@l4desk.ru**.
Для выполнения требования Platerra нужно отдельное правило отправителя
**noreply@platerra.ru** в функции шлюза для device_id `platerra-landing`,
с сохранением прежнего From для остальных каналов. Доступ к функции пока
недоступен из-за истёкшей авторизации `yc`; новый relay остаётся выключенным.
Если требуется изменение, сохранить текущий исходник/конфигурацию и сделать
совместимое адресное изменение, сохраняя sender других потребителей.
Не добавлять непроверенные sender/from поля в JSON API.

`CONTACT_DELIVERY_ENABLED=0` по умолчанию предотвращает отправку через непроверенный
контур. После настройки CAPTCHA и sender установить 1 в игнорируемом env.
На момент подготовки браузерная форма и новый relay не опубликованы;
на сервере работает версия `be0a521` без телефона, с CTA на действующий mailto.

## Настройка и выпуск

1. Настроить адресное правило sender в шлюзе; From тестового письма уже подтверждён как noreply@l4desk.ru.
2. SmartCaptcha для apex проверена; перед выпуском проверить www при необходимости.
3. Проверить/настроить gateway sender и подтверждение домена в Postbox.
4. Заполнить `contact/.env.contact` по `.env.example`, включить доставку.
   Серверный ключ CAPTCHA и gateway URL остаются вне Git.
5. Доставить env по SSH с правами 600, выполнить сборку и выпуск через `deploy/release.sh`.
6. Проверить nginx, CAPTCHA, отрицательные HTTP-запросы, темы и адреса контейнера.
   Положительную доставку проверить реальным сообщением и заголовком From.

## Выполненные проверки

Node build/syntax; Ruff check/format и Pyright; 10 unit tests механизма, включая отключённую доставку,
адаптированных к новым темам. Playwright: все шесть страниц на 1440/768/390/320 px
без переполнения и без телефона; выбор темы terminal по ссылке; блокировка
отправки без CAPTCHA; mock-ответ сервера с корректным payload, статусом и
блокировкой повторной отправки. Реальных писем в этих тестах не отправлялось.

Скриншоты: `website/.preview/contact-form-*.png`, `platerra-captcha-domain.png`.
Документация провайдера: [SmartCaptcha domain validation](https://yandex.cloud/en/docs/smartcaptcha/concepts/domain-validation),
[Postbox SendEmail](https://yandex.cloud/en/docs/postbox/aws-compatible-api/api-ref/send-email).
